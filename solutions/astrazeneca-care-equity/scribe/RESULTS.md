## What was run, and what was not

- **The planned run did not happen.** The plan was a LoRA adapter on `unsloth/gemma-3-4b-it` on a Verda GPU box (NVIDIA A100-SXM4-40GB, `runs/genomics.jsonl`).
  The box was set up (venv, torch 2.15.0, transformers 5.23.0, peft 0.21.3, model snapshot downloaded, 8.1 GB), then stopped answering at 16:31 UTC (last contact 16:29:42 UTC).
  At 17:01 UTC the address answered again with a different SSH host key
  (known `SHA256:DL8CyF/fJUllLqkZIa8QnwXZiPtVNuNIXu2aWtJyn98`, new `SHA256:Ee09o+q1BBreAYd+PL1hPBW68QajVwoxNb3oUia4aKg`). The changed key was not accepted and nothing was run there.
  The same outage is recorded by the other job on that box (`runs/genomics.jsonl`). Run log: "not connected; changed key not accepted; /root/scribe (venv, model cache, dataset copy) presumed lost; 4B CUDA training not run". **No Gemma 3 4B number exists.**
- **The version-1 GPU training could not have run there either.** `scribe/train_lora.py` passes `warmup_ratio` to `TrainingArguments`, which transformers 5.23.0 rejects; that is the version the box had installed (same version). `scribe/run_gpu.sh` installs accelerate, peft, torch, transformers without a version pin, so a fresh run would get the same failure. Checked on 2026-11-14 by `scribe/check_cuda_path.py` (`data/scribe/cuda-path-check-v1.json`). The training attempt itself was never made: no training step on the box is logged.
- **Superseded.** The GPU path is now scribe/v2 (run_gpu.sh pins torch, transformers, peft and accelerate; train.py uses integer warm-up steps). The version-1 CUDA path (`scribe/run_gpu.sh`, `scribe/train_lora.py`, `scribe/evaluate.py`) is kept as it was and has never run on a GPU.
- **What ran instead:** a reduced fallback on the MacBook Pro (Apple M5 Pro, 24 GB) with MLX:
  `mlx-community/gemma-3-1b-it-bf16` (an MLX conversion of Gemma 3 1B instruction-tuned, ungated; Gemma terms apply), not the
  `unsloth/gemma-3-1b-it` mirror named in the plan, and not on CUDA.
  Snapshot `60444cd9d4be58ce6995614c6551b4d8db047483`, converted from `google/gemma-3-1b-it` (licence tag `gemma`);
  weights `model.safetensors`, 2,603,791,060 bytes, sha256 `8fdc602dfc5169e03d379baa2f5c4e239d92dee8685263c6f975e889356c9969`.

## Ground truth against the documented pathway order

`DATA_COLLECTION.md` section 1 fixes one order (`eventlog/schema.py`). The sampler (scribe/sample.py) puts SPECIALIST_VISIT before DIAGNOSIS; SPECIALIST_VISIT before MDT_DECISION; the documented order has them the other way round. Counted against the documented order, 313 of 2466 accepted episodes (12.7%, about one in 8) contain a reversed pair (211 of 1716 training, 42 of 250 validation, 60 of 500 test), and 5 of the 46 Haiku notes. By pair: DIAGNOSIS dated after SPECIALIST_VISIT: 176; MDT_DECISION dated after SPECIALIST_VISIT: 174. Run on the ground truth, `eventlog/validate.py` flags 313 accepted episodes (the same ones) and 5 Haiku notes; its strict mode for simulator output rejects every split. The adapter was trained on the training ones and is scored on the test ones.

Scores without those episodes: adapter note-level exact match on all test notes 38.0% (33.5–42.6; n=440); on the 200 of the first evaluation 42.8% (35.8–50.1; n=180) (base 0.0% (0.0–2.1; n=180)); on the Haiku notes 46.3% (32.1–61.3; n=41). The sampler was not changed and the data were not regenerated: a second dataset version built in parallel depends on the sampler as it is.

## Identical event lists across splits

The sampler (scribe/sample.py) hashes entry route plus events to choose the split, so the same events with another route can land in another split. 7 of the 500 test notes have exactly the event list of a training note (3 of them among the 200 first evaluated; 7 are single-event notes; the adapter got 6 of them right). Without them the adapter's exact match on the test notes is 36.7% (32.6–41.1; n=493). Validation notes sharing an event list with a training note: 1. No id, target (route and events) or note text occurs in more than one split.

## De-duplication of cached rows

The first cached row of an id is kept whatever its verdict. Of 4476 cached rows, 20 ids occur more than once: in 6 the first row was rejected and a later one accepted, in 6 a second accepted note was dropped. Accepted notes of the first kind were dropped and their id filed under rejected; dataset-v1 is left as built because the adapter was trained and scored on it.

## Limits

- Not the planned model, hardware or training length. Nothing here says how Gemma 3 4B would do.
- The base model almost never produces the required JSON shape, so the strict comparison is mostly a format comparison.
  The lenient reading shows the base model is also weak on content (it mostly names one event and the wrong date).
  What the short fine-tune taught is the output format, the event types, the route and copying absolute dates;
  it did not teach date arithmetic.
- The in-sample risk-coverage shares are optimistic by construction. With the cut-off fixed on validation notes no target is shown to hold on the test notes (see that section). Every extraction needs human confirmation until a threshold
  has been validated on real, human-labelled notes.
- About one episode in 8 of the ground truth (313 of 2466) breaks the pathway order that `DATA_COLLECTION.md` now documents (see above).
- Gemma's prohibited-use policy restricts automated decisions in healthcare. Letting extractions into a record without a
  person confirming them would fall under it; this is one more reason the design keeps `verified_by_human`.
- The verifier was called through the floating alias `jev-latest`; the version it resolved to during the dataset build was
  not captured (`data/scribe/provenance-v1.json`).
- Simulated notes are short, one style family, with dates given in 6 fixed forms (month, days, weeks, long, numeric, no_year). Real clinical text is harder.
- Labels are unaudited by humans (see the warning above).

## The version-1 CUDA path is superseded

`scribe/run_gpu.sh`, `scribe/train_lora.py` and `scribe/evaluate.py` were repaired after the first attempt (stop token supervised,
batched decoding, wall-clock cap) but have never run on a GPU, and `scribe/train_lora.py` would stop at `TrainingArguments` under transformers 5.23.0 (rejected: warmup_ratio). Do not use them for the planned run. `scribe/v2/` is the GPU path: `scribe/v2/run_gpu.sh` pins the library versions
and its training uses integer warm-up steps; see `scribe/v2/README.md`.
